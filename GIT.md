# **Git Best Practicies**

### Чек-лист лучших практик для команды в GitLab/GitHub:

1.  **Перед созданием ветки:** всегда `git pull` в `main`.
2.  **Во время работы в ветке:** регулярно (например, раз в день) делай `git rebase origin/main`, чтобы быть в курсе изменений и решать конфликты постепенно.
3.  **Перед созданием Pull/Merge Request (PR/MR):** обязательно сделай финальный `rebase` на `main` (или `merge`), чтобы убедиться, что твой MR/PR можно смержить без проблем.
4.  **Избегай force-push в общие ветки.** Если это необходимо, предупреди команду.
5.  **Используй `git push --force-with-lease`** вместо `git push --force`. Он безопаснее, так как не позволит перезаписать чужие коммиты, которые ты еще не подтянул себе локально.

**Дальше - подробнее.**

### 1) Влили в `main` одну из веток, остальные ветки надо теперь за ребейзить?

Да, и это лучшая практика.

Когда вливаешь (`git merge`) одну ветку в `main`, история `main` продвигается вперед. Все остальные ветки, которые были созданы из более старого коммита в `main`, теперь содержат устаревший код. Это может привести к двум проблемам:

1.  **Конфликты слияния:** чем дольше ветка живет в отрыве от `main`, тем больше вероятность и масштаб конфликтов, когда ты решишь ее влить.
2.  **Проблемы с тестированием:** ты тестируешь свой новый функционал на старом коде, и после слияния в `main` он может сломаться.

**Что делать?**
Регулярно обновлять свои ветки от `main`. Есть два основных способа:

*   **`git rebase` (предпочтительный - чистая история):** коммиты из твоей ветки перемещаются на верхушку актуальной ветки `main`. История становится линейной.

    ```bash
    git checkout my-branch
    git fetch origin                
    git rebase origin/main          
    ```
*   **`git merge` (проще, но создает merge-коммиты):** создаешь коммит слияния, который объединяет твою ветку и `main`. История становится не такой линейной.
    ```bash
    git checkout my-branch
    git fetch origin
    git merge origin/main
    ```

### 2) Один пользователь сделал ребейз и запушил, что должны делать остальные?

**ВНИМАНИЕ!** Перезаписывать историю в общей ветке (которая уже есть у других) - плохая практика.

**Например:** у вас есть общая ветка `feature/auth`. Вы работаете в ней вдвоем. Коллега делает `rebase` своей локальной версии ветки на `main` и делает `git push --force-with-lease`.

**Что делать тебе:**

1.  **Ни в коем случае не делай простой `git pull`!** Это создаст у тебя локально хаос из-за конфликтующих историй.
2.  **Тебе нужно перезаписать свою локальную историю,** приведя ее к виду, который теперь находится на сервере.

**Правильная последовательность действий:**

```bash
# Убедись, что ты в нужной ветке
git checkout feature/auth

# Забери все изменения с сервера, но НЕ сливай их
git fetch origin

# Сбрось свою локальную ветку к тому состоянию, в котором она теперь на сервере.
# Это перезапишет твою локальную историю.
git reset --hard origin/feature/auth
```

**ВАЖНО!**

*   Команда `git reset --hard` **безвозвратно удалит все твои локальные коммиты, которые еще не были запушены в общую ветку**. Если они у тебя есть, их нужно сначала спасти (например, создать от них временную ветку).
*   **Лучшая практика:** договоритесь не делать force-push (`rebase`, `push --force`) в **общие** ветки. Force-push допустим только в твои личные feature-ветки, которыми ты еще не делился с коллегами. Для обновления общих веток используй `merge`.

### 3) Как правильно создать новую ветку?

1.  **Переключись на `main` (или другую ветку, от которой хочешь ответвиться):**
    ```bash
    git checkout main
    ```
2.  **Получи последние изменения из удаленного репозитория и обнови свою локальную ветку `main`:**
    ```bash
    git pull origin main

    # или, что то же самое:
    git fetch origin
    git merge origin/main
    ```
3.  **Теперь, находясь на актуальном `main`, создавай и сразу переключайся на новую feature-ветку:**
    ```bash
    git checkout -b feature/my-new-branch
    ```

**Почему это важно?**
Ты начинаешь разработку нового функционала с самой последней версии кода. Это сводит к минимуму будущие конфликты.
